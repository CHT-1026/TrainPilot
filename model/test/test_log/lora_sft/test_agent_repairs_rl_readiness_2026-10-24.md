## 变更与验证范围

修改保存在独立 Agent 工作树 E:/agent项目/TrainPilot-Agent-RAG，未覆盖旧 Agent 目录。README、模型权重与 V5 原始语料保持原样。未提交或推送 GitHub。

- 公司别名归一：澜图公司、澜图智能与资料全称对齐。无公司名的产品手册可使用已授权索引的 lantu namespace 归属；正文明确的其他公司不能因此冒充澜图。此校验不赋予权限，检索仍使用服务端用户和原 EvidenceScope。
- 多轮路由：仅延续上一轮知识问答的明确指代或省略追问；业务确认、取消、澄清、当前记录查询、公开信息限制和文本改写保持优先。普通聊天后不继续沿用旧知识路由。
- 上下文补全：中文紧邻型号也能跟踪 LT-R20。新问句已有属性时只补主语，不附加旧问题的负载属性；OA追问使用补全后的主题选择资料库，并重新按当前用户检索。
- 型号精排：复用统一的 MODEL_RE，使中文相邻写法同样能触发原有 Pro/普通型号区分规则，未把 Pro 的1750mm当成普通版1700mm。

使用原 LangGraph、真实本地 V5 推理、原检索/重排/引用校验；索引从冻结文件加载。业务采用原服务、权限、确认和审计逻辑，存储为隔离 SQLite。未连接生产 MySQL、Redis，也未验证其并发和持久化特性。
18条给定证据原始模型生成沿用上一轮结果，没有重新生成或重新宣称18/18语义正确。最终RAG/检索来自acceptance；最终25轮工具来自business_final。开发迭代及一次未完成执行另存，不拼成额外通过数。

具体追问流程：上一轮主题跟踪LT-R20 → 原始模型将追问识别成general_chat → 程序识别同主题指代并路由policy_qa → 查询补为“LT-R20的臂展呢？” → 当前用户重新检索 → Pro资料按原型号规则降权 → 模型引用产品参数矩阵回答1,700mm → 通过原校验返回。程序没有把答案1700预写入提示词。

## 保留的失败

1. 单问负载时，模型生成20kg但引用产品概览而不是参数行，程序两次校验失败后抽取式回退。事实数字碰巧正确不等于引用正确。
2. 请假收集首轮“我想请事假，时间和原因稍后补充”漏提取leave_type，导致多问一次；后续可恢复，但完整轨迹不通过。
3. “审批意见：同意安排”被抽取成“安排”，丢失原文。确认后能执行不代表字段保持正确。
4. 上轮给定证据测试的4条错误引用仍是有效失败；此次没有改权重，不能宣称它们已被训练修复。

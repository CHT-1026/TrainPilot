# TrainPilot 严格／分层奖励 GRPO 对照与调试记录

日期：2026-10-30。模型：原 Qwen3-1.7B Full SFT 底座＋V6 LoRA。复核对象：学校服务器返回的 `2026-10-30 22_59_32-2451792377.zip`。本次只读复核与文档整理，没有新增训练或替换模型。

## 结论与处置

本轮分层奖励未通过预先设定的业务及回归门槛，保留严格奖励机制和原始V6权重，不自动采用任何一个新adapter。该结论仅适用于当前奖励、数据与训练预算，不表示分层奖励或GRPO普遍无效。

两seed开发正确数的均值，严格与分层均为58/70。分层seed42较对应严格路线多1题，但旧业务从原V6的63/63下降到60/63；分层seed43没有超过严格路线，规则识别的严重错误也更多。不能选择表现最好的一次实验宣称稳定改进。

严格奖励seed42自身也发生旧业务协议退化。因此“保留严格机制”不等于“部署本轮strict训练结果”，也不能声称严格奖励天然保证安全。

## 问题、假设与修改过程

1. V5/V6专项SFT：旧业务修复不等于新表达组合泛化。V6通过520条修复＋520条旧训练回放，从V5 adapter继续SFT，训练1轮、130次更新。修复状态确认、字段保留及部分证据回答，但出现新漏字段、过度澄清与RAG无依据价格。
2. 输入契约排查：发现Agent默认提示与训练协议不同，统一为TrainPilot七字段意图协议，网页与终端共用构造函数，并传递日期、待确认草稿、历史、摘要和已累计字段。保留权限、草稿版本与执行校验；11项相关检查通过。该接口修复不是模型能力成绩。
3. 能力与选择诊断：冻结训练／开发样本，V5/V6同题多次采样；3900条回答重算一致。V6开发侧贪心56/70，8次采样至少一次正确69/70，说明这批任务上存在正确候选但选择不稳定。不是单次69/70或普遍泛化证明。
4. 奖励假设：二值奖励将不同字段错误压成同分，可能损失有用排序。新增正确、缺失、错误、多余字段诊断，加入关键对象/决定/日期等约束，采用加权字段F1提供部分分数。
5. 验证方式：保留原二值严格成功作为验收，固定起点、数据和超参数，运行两seed的严格/分层对照，并检查旧业务、协议、严重错误和RAG内容，不以训练reward上涨判胜。

## 实验设计与可追溯性

四个trial均从同一份原V6开始，分别建立新优化器；reference也是原V6 adapter，底座共享冻结，不是关闭adapter后的Full SFT模型。训练仅更新策略LoRA；本包不含运行时完整参数快照，因此本次复核不宣称逐参数证明服务器所有底座/参考参数冻结。

| 项目 | 设置 |
|---|---|
| 方法与seed | strict/graded，各42、43 |
| 训练提示 | 同一75条训练侧业务输入，不按新奖励得分筛选 |
| 开发验证 | 70条已使用的开发业务题 |
| 统一回归 | 104条开发题＋165条旧回归，共269题／模型 |
| 评测对象 | 原V6＋4份训练结果，共1345条贪心回答 |
| 计算精度 | BF16底座、FP32 adapter、BF16 autocast |
| GRPO | G=4，同组2次更新，lr=1e-6，KL=0.02，clip=0.2 |
| 预算 | 每trial最多50次有效更新、100组采样 |
| 更新条件 | 组内奖励有差异，且至少一条候选通过关键业务可接受条件 |
| 最终测试 | 未使用保留的150条GRPO测试题 |

固定的是共同更新与采样上限，实际采样组数、输出长度和token成本不同，不能宣称严格等计算量对照。两开发家族与旧开发回归不能替代真实用户独立验收。

## 分层奖励候选

- 截断或无法解析JSON：-1；业务schema不合法：-0.8。
- 意图错误：普通错误-0.6，错误写操作/确认/取消提案-1。
- 意图正确但关键字段错误或无依据多出关键字段：-1。
- 缺少关键字段：最高0.2。
- 其他情况：`0.4 + 0.5 × 加权字段F1 + 0.1 × 严格成功`，仅完整成功为1。
- 字段权重：app_id/decision为4，起止日期为3，leave_type为2，reason/comments为1。

严重错误和协议合法性分别记录；“severe_error=0”不代表没有语义错误，schema错误也不能被忽略。组内相对标准化意味着负分回答仍可能获得正优势，因此关键候选条件与最终严格回归不可省略。RAG没有参与RL，也没有使用参考逐字一致率作为训练奖励。

## 关键失败与调试定位

### 1. JSON结构退化出现在两种奖励中

strict42旧业务的7个新增失败全部为协议错误，graded42对应3个；均包含类似输出：

```text
{"extracted_info":{"leave_type":"病假", ...}}{"intent":"submit_leave"}
```

这是两个拼接的JSON对象，不能解析为单个业务结果。另有确认任务把整个`action_type/draft`塞进extracted_info，违反确认只输出空字段对象的协议。不能通过截取其中一部分或修复输出后重新计算原始模型通过率。

### 2. 开发提升不等于无回归

graded42开发60/70高于strict42的59/70，但仍新增了与原V6相比的普通意图错误，且旧业务只剩60/63。strict43、graded43都出现审批草稿更新时漏decision；另有意见原文少末尾标点，按既有逐字保留契约记不完整。

### 3. RAG分数相同也可能发生真实退化

已人工阅读全部16条发生文本变化的RAG对照：

- strict42、graded42在“TP-5006负载和价格”中，从整体拒答变成回答负载并编造50000元；两者自动前后均判错，但真实性风险增加。
- strict43、graded43在TP-V6-11问题中，将TP-OTHER的999999元明确绑定给目标型号，引用的目标证据并不包含该价格。
- strict43、graded43在已给出采购价后，又说资料没有采购价，出现新自相矛盾。
- graded42也有真实改善：去掉无依据的负载6000，保留有据采购价并说明负载缺失。因措辞不同，严格参考规则未体现该改善。
- 多个版本将某道既有价格幻觉改成整体拒答，减少编造但仍未回答有依据的负载，不能记为完整任务成功。

本次RAG开发企业参考一致均5/16、OA均3/12；旧企业仅strict42为37/47，其余36/47；旧OA均32/37。这些是参考一致数，不是语义准确率。未对全部112道RAG重新构建独立语义准确率，不能据静态分数宣布RAG保留。

### 4. 自然回复也需要回归

strict43的无system职责题出现重复扩展并达到长度上限；既有OpenAI身份错误没有稳定修复。自然回答未以关键词命中自动计通过，不声称角色与执行边界已经可靠。

- 本地大模型权重加载遇到MemoryError后，改在学校4090D运行，维持BF16对照精度，没有用不同量化精度混合比较。
- Windows单元检查读取中文结果时，默认GBK导致UnicodeDecodeError，改为显式UTF-8。
- 新增底座哈希检查时，测试发现signature尚未赋值即被访问，调整到正确位置；未把该错误版本交给服务器。

- 对照模型、配置、数据及代码摘要与冻结包匹配；包内四份导出adapter哈希与评测清单一致。1345条评测、964条rollout回答与200条更新日志重算核对无不一致。

## 解释边界与下一步

观测支持“当前分层配置没有稳定优于严格奖励，且两种路线均可能引发结构退化”。它不证明仅由模型规模、奖励密度、学习率或数据覆盖中的某一个因素造成。小训练池、单一业务RL目标、输出分布漂移与组内相对更新均是待验证因素。

按既定停止条件，不扩大本轮分层训练，也不直接增加相似模板。保留原V6、严格奖励及四份候选。下一步优先对相同失效输入做单步生成/概率回放，定位JSON闭合、字段保留及确认方向的变化；在没有新证据前，不继续修改多个超参数解释结果。生产执行仍由Agent的协议、权限与状态校验拦截，不能把奖励函数当作安全保证。

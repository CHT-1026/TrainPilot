## 二、协议修复：三个真实缺陷（不是配置问题）

### 1. 工具调用格式不兼容（影响最大）

MiMo V2.6 Flash 输出 **XML 风格**工具调用，而非方案约定的 `TOOL {...}`：

```
<tool_call><function>search</function><parameter>query>差旅住宿标准</parameter>…</tool_call>
```

首轮 40 题实测：**44 轮工具调用因格式不匹配被完全丢弃**。模型在空转，
表现为"工具调用数 = 0"或"轮次用尽仍未作答"。

修复：新增 `parse_xml_tool_calls()`（含参数名 `query>值` / `query:值` 两种分隔符解析），
并支持**一轮内多个工具调用**。修复后同一批题的工具调用数从 0 升到 2–5 次。

### 2. reasoning 模型响应字段

Qwen3.8 把全部内容写入 `reasoning_content`，`content` 返回空串。
原代码只读 `content`，导致本地模型"调用成功但内容为空"。

修复：保留 `content` 与 `reasoning_content` 两个字段，正文优先、推理兜底，推理单独落盘供审计。

### 3. 结构化金标准题的作答格式

104 道 `json_object_equal` 题要求"只输出一个 JSON 对象"，模型直接输出裸 JSON
而不带 `ANSWER {...}` 前缀，原解析器视为未作答。

修复：裸 JSON 且为合法对象时同样判为已作答。

### 4. 槽位与量化版本绑定（公平性防护）

`.env.local` 中本地模型变量名为 `BLIND_EVAL_LOCAL_Q6/Q4_*`，
而执行器按 `BLIND_EVAL_{label}` 读取 → C/D 槽位直接报错。
更严重的是：两个槽位指向**同一地址同一 model id**，若不处理，
Q4 的作答会被记到 Q6 名下。

修复：用 `--alias qwen3.8-27b-{Q4_K_M|Q6_K}` 标识实际加载的量化版本，
执行器启动时读取 `/v1/models` 校验，与期望不符则**拒绝执行并报错**。

## 五、本地模型：硬件阻塞，未按方案执行

### 5.1 环境问题（已解决）
- LM Studio **桌面端未安装**，仅 `lms` CLI → `lms server start` 无后端可唤起。
- 解决：直接用其自带的 llama.cpp CUDA 后端起 OpenAI 兼容服务
  ```
  ~/.lmstudio/extensions/backends/llama.cpp-win-x86_64-nvidia-cuda12-avx2-2.67.0/llama-server.exe
  ```
  必须同时把 `vendor/win-llama-cuda12-vendor-v2` 加进 PATH（否则 DLL 找不到，`0xC0000135`）。

### 5.2 硬件约束（无法绕过）
| 项目 | 实测 |
| --- | --- |
| GPU | RTX 5080 Laptop，**16,303 MiB** |
| Q4_K_M 模型 | 16,800 MB（超显存） |
| Q6_K 模型 | 22,431 MB（超显存） |
| 显存占用（Q4） | 15,851 / 16,303 MiB（97%） |
| prefill 速度 | **14–17 tokens/s** |
| 单轮生成（64 token） | **> 400 秒未返回** |

方案要求每题 **8 轮模型交互 / 600 秒时限**。按实测，单轮已超 400 秒，
**单题 8 轮需数十分钟，400 题需数十小时**，在当前硬件上不具可行性。

### 5.3 调试要点（供换硬件后复用）
- 显式设 `-ngl` 会触发 `n_gpu_layers already set by user to 99, abort`，
  **阻止** llama.cpp 的显存自适应 → 必须不设 ngl。
- `-np 1`（单 slot）：4 slot 会各占一份 16K KV cache，挤占显存。
- 首次 D 模型 40 题全部 `api_error`：4-slot 配置下 prefill 仅 34 tok/s，首轮即超时。
- 诊断脚本：`scripts/local_model_diagnose.py`（可复现实测，非推断）。

### 5.4 处置
**未产生任何本地模型成绩。** 既没有把 Q4 结果冒充 Q6，也没有用放宽预算的方式凑数。
方案第 9 节明确"成绩不理想不是停止或换题的理由"，但这里属于**条件不具备**，
与"成绩不好"性质不同，已如实登记为未执行项。

## 八点五、判分器 v5 → v6 校准与最终重判（2026-11-01 08:00）

### 为什么继续改判分器

v4 判分器在人工抽验中暴露出方向相反的问题：**过度严格**。
216 道含"不可判定"语义的题里，有 60 道模型其实答对了（正确指出证据缺口），
却因 4-gram 召回偏低被判错。

### v5 的教训

v5 加入「不可判定语义通道」后**立即引入新假阳性**：
通道一旦成立就短路了实体与数字校验，导致"改一个数字 + 说无法确定"、
"换一个人名 + 说无法确定"共 16 道蒙混过关。**通道必须在实体/数字校验之后求值。**

### v6 的根因修复

v5 收紧后暴露出 v4 时期被宽松判分掩盖的底层缺陷，逐项修复：

1. **语料级人名白名单**（`scripts/build_person_whitelist.py`）
   从 136 篇语料的结构化人名语境抽出 24 个真实人名，并建立语料 2~3 字串全集。
   彻底消除「安全委」「范围需」「章包括」「公司最」这类跨词伪实体。
2. **归一化边界修复**（`norm()`）
   顿号/斜杠/括号/引号/字母数字间空格一律保边界，数字不再粘连；
   千分位改用负向断言（`` 在中文边界上失效）；
   数字保留一位小数（3.8 亿不再变成 4）。
3. **实体校验分层**：人名强校验、型号仅在肯定答案中强校验；
   人名顺序校验降级为软信号（中文表述路径本就不唯一）。
4. **编造人名检测**改为人名槽位 + 编辑距离双轨，逐位置滑动扫描避免 finditer 吞起点。
5. **验证脚本与判分器定义同步**：负类标记词提到模块级，消除定义漂移。
